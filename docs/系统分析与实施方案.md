## 1. 系统解读

### 1.1 两条回路

| 回路 | 介质 | 流向 | 作用 |
|---|---|---|---|
| 一次侧 Primary | 设施冷冻水 | 左下进、左上出（由下向上） | 冷源，经板换带走二次侧热量；比例阀调节一次侧流量 |
| 二次侧 Secondary | 机柜冷却液 | 右上进、右下出（由上向下） | 吸收机柜热量，经板换放热，再由泵加压送往机柜 |

两侧在板换内为**逆流**布置，这是换热效率最高的接法，也决定了控制上的单调性：一次侧流量↑ → 换热量↑ → 二次侧供液温度↓。

### 1.2 流程（按图上箭头方向）

**一次侧：**

```
P10 → Primary inlet → 过滤器 → P11 → Q1(流量计) → T11 → 板换(下进)
    → 板换(上出) → T12 → 比例阀 → P12 → 过滤器 → Primary outlet → P13
```

**二次侧：**

```
P20 → Secondary inlet → P21 → Q2(流量计) → T21 → 板换(上进)
    → 板换(下出) → 水箱 → 泵 → 单向阀 → 安全阀(0.6 MPa)
    → T22 + P22 → Secondary outlet → P23
```

> 二次侧进出口实物上有过滤器，但模拟器按**纯水**处理：不建模滤芯压降、不建模堵塞，因此 `P21 ≈ P20`、`P22 ≈ P23`。过滤器相关报警不在模拟范围内。

**辅助与安全：**

- 水箱：2# 液位传感器、自动排气阀（LQD02）、手动排气口（LQD02）、补液/排水（LQD02）
- 柜内：漏水警报、温湿度传感器
- 二次侧进口：pH 值传感器（选配）
- 过滤器精度：25 μm / 500 目（标配），50 μm / 300 目（选配）

### 1.4 外接压力传感器的含义

P10/P13/P20/P23 装在机柜外侧，属于**现场选装件**：有的项目接、有的不接，甚至接到别的采集器上。这对模拟器有三个直接要求：

1. **点表必须有「存在/不存在」状态**，不能当成永远有值。
2. **数据要满足水力一致性**：纯水假设下，同一节点的多个测点读数应相同——`P10 = P11`、`P13 = P12`、`P23 = P22`。不能给每个点各扔一个随机数，否则控制程序做压差判断时会看到物理上不可能的组合。将来若要模拟滤芯堵塞，只需在这三条关系上加一个 `ΔP_filter` 项，点表不用改。
3. **不存在的点要能被区分**：是「没装」（读 0 / 无此寄存器）还是「装了但坏了」（超量程 / 异常码）。这两者对控制程序的故障处理逻辑要求完全不同。

`P22` 和 `P23` 是同一节点的两个测点（柜内 / 外接），控制程序任选其一即可；不要一个用来算泵扬程、另一个用来做别的判断，否则会因安装位置不同引入偏差。

### 1.5 控制回路推断

1. **主回路（温度）**：二次侧供液温度 T22 与设定值比较 → PID → 比例阀开度。这是 CDU 最核心的闭环。
2. **从回路（水力）**：二次侧压差 `P22 − P21`（或 Q2 流量）→ 泵转速（VFD）。若为定频泵则退化为启停/台数控制。
3. **保护逻辑**：高温（T22）、低流量（Q1/Q2）、低液位、泄漏、超压（0.6 MPa 安全阀前）、泵故障、传感器断线 → 报警/降载/停机。
4. **泵管理**（若双泵）：运行/备用/轮换/故障切换状态机。

### 1.6 控制程序会算的派生量

这些派生量决定了测点必须成对、且位置不能错：

| 派生量 | 公式 | 用途 | 依赖 |
|---|---|---|---|
| 一次侧换热量 | `Q1·cp·(T11−T12)` | 能效、换热衰减 | 柜内 |
| 二次侧热负荷 | `Q2·cp·(T21−T22)` | 负载率、能效比 | 柜内 |
| 泵扬程 | `P22 − P21` | 泵转速闭环目标 | 柜内 |
| 整机一次侧压差 | `P10 − P13` | 设施侧阻力 | 需 P10 + P13 |
| 整机二次侧压差 | `P20 − P23` | 机柜侧阻力 | 需 P20 + P23 |

过滤器压降恒为 0（纯水假设），因此不提供「滤芯堵塞」类派生量；如果以后要加，只需在 `P10/P11`、`P12/P13` 之间插入一个可配置的 `ΔP_filter`。

### 1.7 双泵运行方式

| 模式 | 泵 1 | 泵 2 | 说明 |
|---|---|---|---|
| 双泵同时运行 | 运行 | 运行 | 大负载或要求冗余；两泵并联，流量叠加 |
| 一用一备 | 运行 | 停止 | 常规工况；备用泵出口单向阀关闭，不倒流 |
| 定时轮换 | 主备互换 | | 防止备用泵长期不转而卡死 |

**轮换流程（控制程序侧，模拟器要能测出来）：**

1. 运行计时到（周期可配，常见 168 h / 720 h）→ 启动备用泵；
2. 确认备用泵运行反馈、出口压力建立；
3. 双泵并联运行数秒（bumpless 切换，不能先停后启）；
4. 停原运行泵，确认流量、`P22`、`T22` 无异常；
5. 任一步失败 → 回切原泵并报警。

**模拟器要覆盖的验证点：**

- 切换瞬间双泵并联，`P22` 抬升是否触发 0.6 MPa 安全阀；
- 备用泵启动失败（fail-to-start）时能否正确回切；
- 停运泵的单向阀是否真的阻止倒流（可注入「单向阀卡开」故障）；
- 轮换过程中 `T22` 的波动是否在允许范围；
- 双泵同时运行时，两泵转速不一致（一台漂移）时的流量分配。

**建议的 I/O 接口**（可改）：

| 点 | 方向 | 类型 | 说明 |
|---|---|---|---|
| `pump1_run_cmd` / `pump2_run_cmd` | 控制程序 → 模拟器 | 线圈 | 启停命令 |
| `pump1_speed_cmd` / `pump2_speed_cmd` | 控制程序 → 模拟器 | 寄存器 | 变频给定 0–100% |
| `pump1_run` / `pump2_run` | 模拟器 → 控制程序 | 开关量 | 运行反馈（接触器/变频器） |
| `pump1_fault` / `pump2_fault` | 模拟器 → 控制程序 | 开关量 | 故障反馈 |
| `pump1_speed_fb` / `pump2_speed_fb` | 模拟器 → 控制程序 | 寄存器 | 转速反馈（可选） |

## 2. 模拟器的定位

**接口孪生优先于物理孪生。**

控制程序的 bug，绝大多数不在热力学，而在：量程与单位、字节序、超时与重连、坏点处理、启停时序、报警阈值。所以模拟器第一优先级是「让控制程序以为接上了实机」，第二优先级才是「算得像」。

三条原则：

1. **点表是唯一真相源**：一份 YAML 同时生成 Modbus 映射、HMI 标签、模型变量、文档，杜绝四处手改。
2. **默认实时（1×）运行**：控制程序里的超时、滤波、PID 积分都与墙钟绑定；时间加速只用于离线回归，不能用于在线联调。
3. **故障注入是一等公民**：断线、卡死、漂移、超量程、异常码、TCP 断开，这些才是联调时最需要复现的场景。

## 4. 关键设计

### 4.1 点表（核心资产）

每个点显式声明地址、量程、信号量程、选装状态，避免联调时才发现量纲或换算对不上。

```yaml
signal:
  kind: current
  range: [4000, 20000]   # 4-20 mA，寄存器单位 µA

tags:
  - id: T22
    desc: 二次侧供液温度（主控量）
    kind: ai
    unit: "°C"
    range: [0, 80]
    modbus: { fc: 3, addr: 111 }
    # 32.7 °C -> 4000 + 32.7/80*16000 = 10540

  - id: P10
    desc: 一次侧进口压力（外接，选装）
    kind: ai
    unit: bar
    range: [0, 10]
    presence: optional          # always | optional | absent
    present: true
    modbus: { fc: 3, addr: 100 }

  - id: VALVE_CMD
    desc: 比例阀开度指令
    kind: ao
    unit: "%"
    range: [0, 100]
    modbus: { fc: 3, addr: 200 }
    writable: true
```

要点：

- **原始信号**：寄存器是 4–20 mA 对应的 µA 值（也可配成 mV 或 ADC 码），工程换算由控制程序完成。模拟量统一 u16，不再有 32 位浮点和字序问题。
- **可选点**（P10/P13/P20/P23）用 `presence: optional` 表达。缺失时输出 0；控制程序应把 0 当作未安装/断线。
- **同一管路的点由同一状态推导**：纯水假设下 `P10 = P11`、`P13 = P12`、`P23 = P22`，不是独立随机量。
- **双向点**（如阀门指令）要区分「控制程序写进来的值」和「执行器实际位置」，后者带行程时间和死区，二者不等才是真实情况。
- **故障态**要能表达成控制程序认识的形式：断线给 0 或超量程、坏点给异常码 0x04。
- 提供 `--dump-points` 自检模式，打印每个点的寄存器地址、量程与信号量程，用于和 PLC 点表逐条核对。

### 4.2 协议

- **首选 Modbus TCP 从站**：绝大多数 PLC/上位机是主站，模拟器当从站即可，无需改控制程序。
- 非特权端口默认 `1502`，可配 `502`（Windows 上 502 需要管理员）。
- 支持 FC 01/03/05/06/15/16；模拟量统一 u16 原始信号，地址由点表决定。
- 多客户端并发：控制程序 + 调试工具同时连接不能互相踢掉。
- **异常注入**：按计划返回 exception code、延迟应答、主动断链，用来测控制程序的重连与超时。
- 若控制程序走私有协议/OPC UA，`cdu-protocol` 用 trait 抽象，加一个 adapter 即可。

### 4.3 物理模型

不必上 CFD，集总参数 + 一阶惯性足够复现 90% 的联调场景。

**板换（逆流 ε-NTU）：**

```
Cr  = Cmin / Cmax,  NTU = UA / Cmin
ε   = (1 - e^(-NTU(1-Cr))) / (1 - Cr·e^(-NTU(1-Cr)))
Q   = ε · Cmin · (T21 - T11)
T22 = T21 - Q / C2
T12 = T11 + Q / C1
```

**因果方向很重要**：机柜负载决定二次侧回水温度（`T21 = T22 + Q_load/(m2·cp)`），板换决定供液温度 `T22`，比例阀改变一次侧流量 `m1` 从而改变 `C1`。这样阀开度↑ → 供液温度↓，闭环单调，PID 才调得动。

**泵与水力（双泵并联）：**

```
单泵扬程  H_i = a·n_i² - b·q_i²      (n_i 为转速比，运行泵)
停运泵    q_i = 0                     (单向阀关闭)
并联约束  P22 - P21 = H_1 = H_2
总流量    Q = q_1 + q_2
管路阻力  P22 - P21 = R·Q²
```

同速双泵对称时 `q_1 = q_2 = Q/2`，与管路方程联立解出 Q；单泵运行时另一台 `q = 0`，工作点落在单泵曲线上。泵启停不是瞬时，转速用一阶惯性（τ ≈ 2–5 s）过渡，切换瞬态才有意义。单向阀卡开故障允许停运泵倒流，这会让 `Q2` 和 `P22` 出现异常，是双泵逻辑的好测试用例。

**水箱：**

```
dV/dt = m_makeup - m_drain - m_leak
level = V / A
```

**传感器：** 一阶惯性 `τ·dy/dt + y = x`，叠加量化（如 12 bit）、噪声、量程钳位。τ 取 2–5 s（温度）、0.5 s（压力），这直接决定控制程序里滤波参数是否合理。

**安全阀：** `P22 > 0.6 MPa` 时泄放，压力钳位并置报警。

### 4.4 故障与场景

场景用 YAML 描述「时间 → 事件」：

```yaml
duration: 1800
seed: 42
events:
  - { at: 0,    set: { load_kw: 40, T11: 32 } }
  - { at: 300,  step: { load_kw: 80 } }          # 负载阶跃
  - { at: 600,  fault: { tag: T22, type: stuck } }
  - { at: 900,  fault: { tag: pump1, type: trip } }
  - { at: 1200, comm: { drop_tcp: 5s } }
  - { at: 1500, set: { pump1_run: false, pump2_run: true } }   # 轮换切换
  - { at: 1700, presence: { tag: P10, present: false } }
```

故障类型：`stuck`（卡死）、`drift`（漂移）、`open`（断线）、`noise`、`out_of_range`、`delay`、`exception`、`actuator_jam`、`pump_trip`、`leak`、`low_level`。

## 5. 里程碑

| 阶段 | 内容 | 验收标准 | 预估 |
|---|---|---|---|
| **M0 接口打通** ✅ | 点表 + Modbus TCP 从站 + 手动/静态值 + 可选点开关 + 双泵命令/反馈 | 控制程序连上，读到全部点，能写阀门与两路泵，连续 1 h 无超时；P10/P13/P20/P23 在线插拔（present ↔ absent）行为符合预期；模拟器能按控制程序的轮换命令切换主备并给出运行/故障反馈；点表逐条核对通过 | 1–2 天 |
| **M1 稳态热模型** ◐ | 板换 + 阀 + 泵 + 负载 | 阀开度阶跃后供液温度单调收敛，能量守恒误差 < 1% | 2–3 天 |
| **M2 动态与故障** | 水箱液位、安全阀、传感器惯性、故障注入 | 泵停/阀卡/断线场景下，控制程序按预期报警并安全停机 | 3–5 天 |
| **M3 场景与回归** | 场景脚本、CSV 记录、golden trace 对比 | CI 中 5 个场景稳定通过 | 2–3 天 |
| **M4 HMI / HIL** | Web P&ID、趋势、强制值；可选 RTU 串口接真实 PLC | 演示可用；HIL 按需 | 按需 |

**M0 的性价比最高**：它不依赖任何物理精度，却能让控制程序先跑起来，同时把点表这个最容易出错的环节一次性对齐。

## 6. 风险与坑

1. **点表来源不可靠** → 优先从现有控制程序代码/文档反推，或对实机抓 Modbus 包；先做「点表对齐清单」再写代码。
2. **通信超时** → 应答任务要与 UI/日志解耦，不能因为画曲线卡住而从站不响应。
3. **字节序与缩放** → 每个点显式配置；提供原始寄存器扫描模式。
4. **过度追求热工精度** → 先保证单调性和时间常数合理，再用实机数据做参数辨识。
5. **时间步进漂移** → 用单调时钟累积 dt，不要用 `interval` 次数乘周期。
6. **双泵/轮换** → 状态机要显式建模「运行/备用/故障/轮换」，否则测不出切换逻辑的 bug。

## 7. 待确认

1. 控制程序跑在什么平台、与 CDU 之间走什么协议？（PLC Modbus TCP / 上位机私有 TCP / 串口 / OPC UA）
2. 模拟器形态：纯软件从站 / 需要接真实 IO 的 HIL / 只要 HMI 演示？
3. 控制策略是否已定：比例阀控 T22 + 泵变速控 `P22 − P21`？还是要对比多种策略？
4. 双泵是**变频泵**还是定频泵？同时运行时是同速还是各自调速？轮换周期多长（168 h / 720 h）？
5. 轮换时控制程序是「先启后停」还是「先停后启」？前者需要模拟器支持双泵并联瞬态。
6. P10/P13/P20/P23 如果接了，是接到 CDU 控制器，还是接到别的采集器？这决定它们是否要出现在 Modbus 点表里。
7. 热工精度要求：一阶集总够用，还是需要更接近实机的响应？

## 8. 向通用液-液 CDU 演进

目前 `tags.yaml` 已经覆盖「点」这一层：位号、地址、信号、量程、单位、噪声、系统图位置。换一台 CDU，只要点表不同，I/O 和页面点位就能跟着变。

但「设备拓扑」这一层还是写死的：

| 层 | 写死的内容 |
|---|---|
| `PidDiagram` | 四条固定管段、板换位置、比例阀固定在 330、两台泵固定在 705；动画读 `Q1`/`Q2` |
| `ControlPanel` | `VALVE_CMD`、`PUMP1/2_RUN_CMD`、`PUMP1/2_SPEED_CMD` |
| `KeyMetrics` / 状态条 | `T22`/`T21`/`P22`/`P21`/`Q2`/`VALVE_POS` |
| `Plant` | 一台板换、两台并联泵、一个比例阀、液位恒定 |

要做到「改点表就适配任意液-液 CDU」，还需要一个 `topology` 段，把管段和设备显式描述出来：

```yaml
topology:
  segments:
    - { id: p_in,  loop: primary,   direction: forward, label: 进水 }
    - { id: p_out, loop: primary,   direction: reverse, label: 出水 }
    - { id: s_in,  loop: secondary, direction: reverse, label: 回水 }
    - { id: s_out, loop: secondary, direction: forward, label: 供液 }
  equipment:
    - { id: HX1, type: heat_exchanger, segments: [p_out, s_in] }
    - { id: V1,  type: valve, segment: p_out, order: 15,
        cmd: VALVE_CMD, pos: VALVE_POS }
    - { id: P1,  type: pump, segment: s_out, order: 20,
        run_cmd: PUMP1_RUN_CMD, run: PUMP1_RUN,
        speed_cmd: PUMP1_SPEED_CMD, fault: PUMP1_FAULT }
    - { id: P2,  type: pump, segment: s_out, order: 20,
        run_cmd: PUMP2_RUN_CMD, run: PUMP2_RUN,
        speed_cmd: PUMP2_SPEED_CMD, fault: PUMP2_FAULT }
```

传感器则从 `place: {loop, branch, order}` 改成 `place: {segment, order}`，段的方向和所属回路由 `segments` 定义。

渲染规则：`segments` 决定画几条管段和流向；设备按 `order` 落在管段上，同 `order` 的两台泵画成并联；`type` 决定图标。这样单泵、无水箱、不同阀位、不同测点数量的机型都只改配置。

模拟器侧同步把设备映射读进来：泵的数量、阀的命令/反馈点不再写死；板换仍是一台（液-液 CDU 的典型结构）。

分阶段：

1. `topology` 解析 + 校验 + `--dump-points` 输出拓扑
2. 前端按 `segments`/`equipment` 渲染，去掉写死的坐标和位号
3. 模型按拓扑读取泵/阀映射（支持 N 台泵、1 个阀）
4. 变体验证：单泵、无水箱、多测点

不在范围内：任意管路图求解、多板换、混流/串联复杂网络——那需要真正的网络模型，另立项目。
